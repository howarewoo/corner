## Stage, compatibility, and retained data

- Corner is unreleased, in development/evaluation, and has no active users. Revisit these instructions when consumers or compatibility commitments change.
- There is no backwards-compatibility requirement for external clients or versions. Within the requested scope, update affected in-repository callers, tests, and docs together and remove superseded implementations. Do not retain aliases, dual paths, or compatibility shims solely for hypothetical consumers. Existing supported workspace-import and recovery guarantees remain requirements.
- Retained data is not disposable: preserve local records/keys, staging synthetic records/Auth/keys, production data, backups, and historical receipts. Migrate retained data when necessary; the absence of active users does not authorize resets. Follow [README.md](README.md#data-backups-and-upgrades) and [HOSTING.md](HOSTING.md) for preservation and recovery; only explicitly authorized owned-local resets are permitted.

## Shared UI first

Always prioritize the shared shadcn/Base UI primitives in `packages/ui` and their live examples in `apps/design` when adding or changing product UI. Inspect and reuse the existing `@packages/ui` component and its shipped styling before using an app-local control or building a custom equivalent. This includes feedback: use the shared Base UI `Toaster` and toast manager for notifications. Do not recreate primitive markup, interaction behavior, or component CSS in the app. If a required capability is missing, extend the shared component rather than creating a parallel app-only implementation. Preserve unrelated legacy controls until their own flow is changed.

Use the root `pnpm-lock.yaml` and `pnpm-workspace.yaml`; setup is `pnpm install --frozen-lockfile` from the repository root when dependency installation is authorized. Do not create workspace lockfiles. Manifest scripts, [turbo.json](turbo.json), and [CI](.github/workflows/ci.yml) remain authoritative.

## Test placement

Colocate tests in a folder named `__tests__` beside the module or feature they exercise. Use the nearest owning source directory rather than a centralized workspace-level `tests/` folder; configuration tests belong beside the configuration they cover.

Server suites use [scripts/test.mjs](scripts/test.mjs), which discovers immediate `apps/server/tests/*.test.ts` files and recursively discovers colocated `src/**/__tests__/*.test.ts` files. Production server output excludes colocated tests. Web suites use [vitest.config.ts](apps/web/vitest.config.ts): colocated `src/**/__tests__/**/*.test.ts`/`*.test.tsx` plus configuration tests in `apps/web/__tests__`. Playwright discovers only colocated `*.browser.ts` files through [playwright.config.ts](apps/web/playwright.config.ts); keep runner discovery disjoint.

A layout migration must update discovery, relative imports, and TypeScript include/exclude rules together, preserving per-file process isolation and keeping colocated tests out of production server output. Do not add tests that the configured runner silently skips.

## Select verification for the change

- **Domain schemas, calculations, or mutation rules:** run `pnpm run check`, consuming server/web suites, and the build. Nutrition, training, and workspace exports compile into their owning `packages/<domain>/dist`; direct workspace commands do not automatically rebuild dependencies as Turbo does.
- **UI behavior:** run the relevant Vitest web suite; run `pnpm run test:browser` when account, food-log, or workout journeys are affected. Inspect the actual changed screen at desktop and phone widths. Component tests and emulated WebKit do not prove real-iPhone usability.
- **Account lifecycle:** run affected server/web suites. Mail fixtures are simulated; no live email without explicit authorization.
- **HTTP runtime, origin/proxy handling, development configuration, or workspace integration:** build, then exercise the relevant production/development smoke checks. Broaden to both smoke checks when changing the shared startup/origin contract.
- **Deployment:** use the checks and manual account/recovery scenario in `HOSTING.md`. Node smoke success does not prove Docker execution, certificates, inbox delivery, or live model access.
- **Documentation only:** check local paths, anchors, commands, and source claims. Do not install dependencies or launch application/provider workflows just to validate prose.

PR, staging, and main CI always install the frozen lockfile plus Chromium/WebKit and run `pnpm run verify -- --full`: native CI/release regressions, root `check`, server/web suites, all workspace/Worker builds, Playwright journeys, and production/development/Workers smokes. Targeted profiles are local only; no activation or advisory CI gate exists. Required checks use ordinary GitHub Actions repository-writer trust. [README.md](README.md#targeted-verification-and-merge-protection) owns explicit protection configuration and timing procedures. Server suites, browser journeys, and runtime smokes require disposable `CORNER_TEST_DATABASE_URL`, never the real `DATABASE_URL`; fixtures create/drop only their own random schemas. Configured commands are not evidence of execution.

[scripts/test.mjs](scripts/test.mjs) runs server files sequentially in separate processes. Vitest runs web files sequentially with `pool: 'forks'`, `isolate: true`, and `fileParallelism: false`; use jsdom only for component suites and explicit RTL/mock/query cleanup. Preserve per-file isolation. Playwright uses one worker, independent synthetic accounts/contexts, and the owned disposable runtime rather than a user's development server. Its controlled provider redirects block service workers to keep interception reliable; ordinary persistence journeys retain them. No measured test-performance bottleneck is established.

All runtime smoke scripts use actual disposable PostgreSQL schemas and a local HTTPS Better Auth fixture; no real email/model request is made. Better Auth is a test-only dependency. Development smoke runs web/API/landing/shared development tasks, not the independent catalog, and rejects root `.env`, `.env.local`, `.env.development`, and `.env.development.local`. Use a clean checkout/snapshot; never remove or rename a user's configuration to make it run. Keep owned-process/schema cleanup rather than killing unrelated listeners.

## Persistent integration and releases

After the explicit live cutover in [HOSTING.md](HOSTING.md#one-time-protected-configuration-and-cutover-order), start ordinary feature branches from `staging` and target feature PRs there. `staging` is persistent/default; `main` is production. The foundation PR must first land on main; do not infer that live defaults/protections already changed from this documentation alone.

Promote staging to main with a merge commit, then synchronize main back into staging after every release and emergency main hotfix. If diverged, use a temporary sync branch based on current staging, merge main into it, and pass CI before its PR merges into staging; never bypass strict up-to-date checks. Never delete, force-push, or replace either persistent branch. Feature branches use local checks, not per-feature Neon or Cloudflare previews. Staging retains synthetic records on its own schema-only Neon branch in the existing project, independent Auth/keys, and an approved-testers-only stable origin.

Production is one full-stack Worker named `corner`; staging is native Preview `staging` under that existing Worker, not another named Worker. Both use the identical immutable format-4 bundle/assets/Drizzle migrator without rebuilding. Expected origins are `https://corner.adam-nathaniel-woo.workers.dev` and `https://staging-corner.adam-nathaniel-woo.workers.dev`; an exact production HTTPS custom domain is optional. Keep `preview_urls` enabled, Access limited to the exact staging alias and deployment URLs, and production outside Access. No frontend Worker or service binding remains. Preserve isolated staging Neon DB/Auth/keys and synthetic records. Staging is the review surface; merging to main is production release approval. Successful exact current trusted main push CI automatically dispatches `release.yml` on main through `production.yml`, qualifies/promotes the immutable artifact, and records one version in the format-4 `corner-release` / `corner-production` receipt after public checks. Every production mode uses the existing main-only `production` environment and credentials, without reviewer/wait-timer rules or human-attestation JSON. Explicit bootstrap/Worker adoption/recovery still require deliberate dispatch and exact operation pins; all modes complete after automated qualification, live-version verification, and public checks. Automatic staging uses separate format-4 `corner-preview` / `corner-staging-preview` journals after successful exact current trusted staging push CI. Pre-Drizzle artifacts are not upgrade/recovery targets; no historical executor or archive is retained. The completed one-time pre-Drizzle database cutover paths are retired; preserve native migration history, old audit metadata, all records/Auth/keys, and historical receipts. Empty schema-only staging baselining remains a separate verified provisioning operation, never a reset of populated staging. An operator-provisioned `corner` can host staging before its first production release; trusted triggers/controllers must be merged onto the applicable branches before automation is active. First-release Worker adoption requires explicit bootstrap and an exact `provisioned_version_id` pin, rechecked before SQL and deployment. It does not invent qualified history. Preserve installation keys/data, register exact Auth origins, and never recreate removed legacy Workers. Disable independent Cloudflare Builds/automatic Preview triggers. Live GitHub policy/credential changes, bootstrap/recovery, cloud administration, and retirement remain separately authorized operator work. Source edits do not establish live cutover; follow [HOSTING.md](HOSTING.md#one-time-protected-configuration-and-cutover-order).

The dual-origin cutover supersedes the incumbent production URL choice above: production requires an explicit HTTPS root/app-subdomain pair, with `CORNER_ORIGIN` remaining the app origin and `CORNER_LANDING_ORIGIN` the root. Preserve the existing exact staging app alias and supply an explicitly approved additional landing-preview origin; protect both staging sites and native deployment URLs with Access. Do not guess/provision hostnames, widen app Auth/CORS/cookie domains, or expose API/OAuth/MCP on landing. Existing single-site format-4 artifact inventories/receipts remain immutable supported recovery inputs. Follow HOSTING.md for the separate origin-cutover, PWA/re-login and OAuth/MCP reconnection gates.

## Boundaries and pitfalls

- Package names follow their folders: `apps/<name>/package.json` uses `<name>`; `packages/<name>/package.json` uses `@packages/<name>`.
- Import domain code through its owning `@packages/nutrition/<module>`, `@packages/training/<module>`, or `@packages/workspace/<module>` export, never relative paths into another workspace. Keep credentials, database access, and external I/O server-side.
- Preserve owner-scoped reads/writes, original request fingerprinting, atomic state/receipt commits, and record-level concurrency. Ordinary manual mutations do not all carry `expectedRevision`.
- All assistance, model connections, and request/review mutation commands are retired. Preserve historical recipe/training request/review schemas and import/export without restoring executable archive commands.
- Data paths resolve from the repository root. Preserve existing private configuration, encrypted provider archives, AI-run rows, original keys, backups, migrations, and receipts. Never regenerate or expose keys. Application runtime requires no model secrets; local controller Auth/password/control secrets and TLS remain independent and required.
- Keep the existing one-process Node topology and transaction-scoped owner locks. Final retirement release requires separate owner/operator backup confirmation and revocation of any existing ChatGPT grants; source removal is not evidence those gates passed.
- Neon Auth owns managed accounts, sessions, and SMTP. Register the exact application origin; configure OTP verification and keep `NEON_AUTH_REQUIRE_EMAIL_VERIFICATION` aligned with the branch policy. `DATABASE_URL` is pooled; use `DATABASE_URL_UNPOOLED` for explicit migrations and backups.
- [scripts/package.py](scripts/package.py) uses an explicit root-file allowlist. It currently omits `AGENTS.md`, `PRODUCT.md`, `DESIGN.md`, and `ARCHITECTURE.md`; these guides are repository-checkout guidance, not contents of the generated source ZIP. Packaging changes are separate implementation work.
