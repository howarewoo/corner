The product apps import compiled subpaths directly from the owning domain package. Nutrition and training are independent leaf domains; workspace composes their state and mutations; agent validates proposals against that composition. The API contract depends on these domain contracts without owning their rules. Domain packages do not own HTTP, storage, account credentials, or provider calls. Server I/O stays server-side; web components render state and send authenticated requests.

The workspace shell composes feature screens from `apps/web/src/features`: `today`, `meal-planner`, `recipes`, `groceries`, `recipe-studio`, `food-log`, and `settings`. The authenticated root loads only settings/revision/AI availability; feature-owned resource queries load bounded calendar slices, cursor pages, details, and aggregates. [resources.ts](apps/web/src/features/workspace/resources.ts) composes same-revision calendar dependencies and follows explicit continuations before treating a slice as complete. [use-workspace-state.ts](apps/web/src/features/workspace/use-workspace-state.ts) owns preview-local full-state edits, manual mutation serialization, and shared notifications; live writes never reconstruct lifetime `AppState`. The shell retains the selected date and keeps recipe filters and studio drafts mounted across navigation. [workspace-overlays.tsx](apps/web/src/features/workspace/workspace-overlays.tsx) coordinates the existing shared-primitive dialogs.

Only the product uses React Router in declarative mode, with a `BrowserRouter` at its entrypoint. Its route table in `corner-app.tsx` selects Today (`/`), `/agent`, `/workouts`, `/planner`, `/recipes`, `/groceries`, `/studio`, and `/settings`; workspace state stays mounted across these routes. Unknown workspace paths replace the current history entry with `/`. Session loading gates workspace access without discarding a requested destination; new accounts need no onboarding or completed profile. Settings owns optional profile editing and the previewed, empty-workspace import in [import-workspace.tsx](apps/web/src/import-workspace.tsx). Password-reset links retain their fixed `/account/reset-password` path, validate the token before consumption, and replace the sensitive query through the router. Storybook replaces the custom catalog router shell and owns catalog history: canonical links are `?path=/story/<group-lowercase>--<id>`; legacy `?component=<id>` links redirect to the corresponding story. Shared UI components accept rendered links rather than importing a router; product callers supply React Router `Link` elements, while catalog links target the top-level manager.

[theme.tsx](apps/web/src/theme.tsx) owns the product's browser-local Light/Dark/System preference, resolves live system changes, and aligns the document's `data-corner-theme`, `.dark` class, and browser theme-color metadata. `ThemeProvider` wraps account entry and the workspace. Shared `ThemePicker` and optional `AppSidebar.theme` remain controlled UI; they do not access storage or workspace data. The catalog bridges its independent Storybook theme global through `src/catalog-theme.ts` and resolves it in its preview provider.

Neon is managed infrastructure, not another deployable application. Root [neon.ts](neon.ts) configures Auth and branch policy; database access, the managed Auth proxy, and application SQL migrations remain owned by `apps/server`. There is no separate Neon app or database package.

## Runtime and origin boundary

Development runs product Vite on browser port `3000`, the API on loopback port `3001`, nutrition/training/workspace/agent/API compiler watchers, and the independent design catalog on `3002`. [vite.config.ts](apps/web/vite.config.ts) proxies `/api` and `/auth/callback` without rewriting the canonical browser Host/Origin. Turbo builds domain/API dependencies before consumers; see [turbo.json](turbo.json).

The `pnpm run dev` controller in [scripts/local-dev.mjs](scripts/local-dev.mjs) always isolates development from cloud Neon. [compose.local.yaml](deployment/compose.local.yaml) supplies owned PostgreSQL 17; [local-runtime.mjs](apps/server/scripts/local-runtime.mjs) starts a persistent HTTPS Better Auth fixture after explicit application migrations. Native `pg` remains unchanged. Controller and child environments are scrubbed; no development entrypoint loads root environment files. API development requires local mode and loopback database/Auth endpoints, rejecting database host overrides before connections or private-key writes. The controller runs the existing Turbo API/web/catalog/compiler tasks; optional loopback port selection changes the browser/API/catalog together.

The explicit seed operation reaches only a private Unix controller socket. It verifies Compose container/volume ownership and database identity before preparing the local runtime. [local-services.mjs](apps/server/scripts/local-services.mjs) reserves deterministic fixture account IDs and seed dates in development-only bookkeeping tables, creates accounts through Better Auth, and imports synthetic workspaces through authenticated native RPC. Durable completion records preserve edited fixtures beyond bounded mutation-receipt retention. The local fixture's Auth tables share its private database schema; hosted `neon_auth` lifecycle remains Neon's responsibility. No seed code is part of application migrations, Worker entrypoints, or release hooks; no staging/production seed target exists.

Local shutdown retains database records and `.corner-local/` keys. Explicit reset validates ownership before deleting only its database volume. The ignored private directory is also excluded from Docker contexts; existing `data/`, environment files, and hosted secrets remain untouched. The fixture supplies no mail delivery or AI credentials and does not establish managed Neon Auth parity.

[local-migrations.ts](apps/server/src/local-migrations.ts) handles the owned local database's transition to native Drizzle history before invoking the ordinary migrator. Under the migration lock, it checks the local installation identity and validates existing application definitions against an isolated schema created from the initial checked-in Drizzle SQL. A matching pre-Drizzle database with its old audit ledger and absent/empty native history receives only a native baseline entry; application/Auth records, seed state, and historical audit metadata remain untouched. Temporary reference DDL and baseline writes are transactional. This path is not used by hosted startup, deployment migrations, or staging provisioning.

Production runs compiled JavaScript from `apps/server/dist`; the same Node process serves `apps/web/dist` and API routes on one origin. It runs neither Vite nor a TypeScript loader. The hosted template adds Caddy in front of this process, not a second application backend.

Both runtime entrypoints call the same Hono app's `fetch` handler. Native oRPC procedures under `/api/rpc` replace all handwritten application REST routes. The shared `@packages/api` contract defines account, workspace, AI, and agent procedures; browser calls use an oRPC client and TanStack Query server-state cache. Native requests carry `{json: input}`, successes `{json: output}`, and errors `{json: {defined, code, status, message, data}}`; `SIGN_IN_REQUIRED` and `CORNER_ERROR` (with `data.code`) retain application error semantics. Session ownership, canonical Origin, procedure-specific body limits, and renewal cookies apply to RPC successes and failures. Managed Auth `/api/auth`, OAuth `/auth/callback`, and `GET /api/health` stay outside oRPC.

[rpc.ts](apps/server/src/rpc.ts) authenticates the original Request, enforces exact Origin and procedure-specific streaming JSON limits, then passes the parsed envelope to oRPC's public standard adapter. Managed Auth and OAuth still receive the original session context; the transport never normalizes a mutation before the store fingerprints it. Node's upload bridge permits a native error response before closing rejected, unread uploads rather than poisoning a reusable HTTP connection.

[rpc.ts](apps/web/src/rpc.ts) owns the browser QueryClient, native client, private session-lifetime/parameter keys, and resource-family revision floors. Read-only workspace resource queries retry only `ACCOUNT_SERVICE_UNAVAILABLE`, at most twice after 500 ms and 1,000 ms; exhaustion retains the existing error and manual Retry. TanStack Query cancellation stops backoff on logout, expiration, or invalidation. Mutations, account queries, provider queries, and other errors do not automatically retry; drafts, filters, and preview edits remain local. Revision-only writes invalidate their affected resource families, cancel pending reads, and raise floors even for not-yet-created keys. Both response resolution and Query ingestion reject stale pre-write revisions and retired session lifetimes, including a later login by the same account. Logout/expiration clear private query and mutation caches. Provider connection reads do not refetch on focus/reconnect. Active agent runs poll every two seconds, including in the background, and stop when terminal.

The [web manifest](apps/web/public/manifest.webmanifest) and Apple Home Screen metadata provide standalone installation on the same origin. [pwa.ts](apps/web/src/pwa.ts) registers the root-scoped [service worker](apps/web/public/sw.js) only in production builds, after page load. It handles same-origin GET document navigations with network-only fetches and a self-contained, no-store offline recovery response; API, Auth, account-recovery, non-navigation, and write requests remain untouched. It uses no Cache Storage, offline mutation queue, or forced worker activation/reload, so installation adds no persistent private-data cache or stale-shell fallback. Both runtimes serve these public assets through their existing static security boundary; Node explicitly supplies the manifest MIME type.

[config.ts](apps/server/src/config.ts) resolves data paths from the repository root, independent of workspace working directory. [index.ts](apps/server/src/index.ts) validates the canonical Host; account and workspace writes also require the configured origin. [request-identity.ts](apps/server/src/request-identity.ts) accepts forwarded client identity only with the configured proxy proof. Preserve these boundaries when changing the proxy or callback path; do not trust arbitrary forwarding headers. Deployment details remain in [HOSTING.md](HOSTING.md#proxy-boundary).

Cloudflare Workers use [wrangler.jsonc](apps/server/wrangler.jsonc) to bundle the same web assets and a native Fetch entrypoint. All requests run through the Worker before asset serving, preserving canonical-origin checks, API no-store policy, static security headers, and account-reset deep links. [runtime-config.ts](apps/server/src/runtime-config.ts) validates both runtimes; the Node-only [config.ts](apps/server/src/config.ts) adapter resolves repository paths and generates/reads keys only when explicit secrets are absent. Workers require explicit secret bindings and never import that filesystem adapter at runtime.

Production is one full-stack Worker named `corner`, using [apps/server/src/worker.ts](apps/server/src/worker.ts) for assets, API, and callbacks, plus the packaged [apps/server/src/maintenance-worker.ts](apps/server/src/maintenance-worker.ts) gate (`worker/maintenance-worker.js`) for explicit operator-driven maintenance cutovers. There is no frontend Worker or service binding. One immutable format-4 artifact supplies `wrangler.json`, `worker/worker.js`, `worker/maintenance-worker.js`, assets, Drizzle SQL/journal/snapshots, and `migration/dist/migrate.mjs` to production and staging without rebuilding. The packaged configuration names `corner`, binds `ASSETS` and `CF_VERSION_METADATA`, disables `workers_dev`, and enables `preview_urls`. Production enables `workers_dev` only for its exact stable `https://corner.<account-subdomain>.workers.dev` origin; HTTPS custom-domain production keeps it disabled. Initial expected production origin is `https://corner.adam-nathaniel-woo.workers.dev`. Deployment/Preview URLs are not production canonical origins. Independent Cloudflare Builds remain disabled.
Staging is one [native Cloudflare Preview](https://developers.cloudflare.com/workers/previews/) named `staging` under `corner`; an operator-provisioned parent can host staging before its first production application release. It consumes the identical full-stack payload with explicitly isolated staging database/Auth/keys. Expected stable origin is `https://staging-corner.adam-nathaniel-woo.workers.dev`; preview-only Access must protect that exact hostname and deployment URLs while production stays outside Access. Keep top-level `preview_urls` enabled. Native Preview configuration, not aliased Version URLs or service bindings, supplies resource isolation. Its existing schema-only Neon branch retains synthetic records and keys across merges and has no expiry. [staging-baseline.ts](apps/server/src/staging-baseline.ts) verifies an empty initial copied schema against read-only source metadata and checked-in Drizzle SQL before writing only native migration history; it is not a routine reset of populated staging. No per-feature app/database previews or production fallback exist. Never recreate removed legacy Workers. The first tracked production release can explicitly adopt the current provisioned version, pinned before migration and deployment; this creates no fictitious qualified history. Automated qualification, live-version verification, and public checks gate production's one-version format-4 `corner-production` receipt; staging uses its separate format-4 `corner-staging-preview` ledger after successful exact current trusted staging push CI. These are implementation contracts, not evidence of live cutover. See [staging setup](HOSTING.md#persistent-staging-database-and-auth).

Main's native repository ruleset requires a successful `staging` environment deployment as well as full CI before merge, with no bypass actors and no deployment rule on staging itself. Preview migration and deployed journals carry terminal success/failure statuses; only verified completion records a successful serving deployment. Public readiness waits for the exact uploaded version, but security-boundary failures are not retried. A pinned staging completion operation verifies immutable artifact/configuration, current schema/serving journals, live bindings, and public behavior without migration, upload, or production traffic changes.

The Worker creates/closes one Neon WebSocket pool within each API request through [worker-database.ts](apps/server/src/worker-database.ts); connections are never cached across isolates/requests. Drizzle's `neon-serverless` adapter preserves interactive transactions on one connection. HTTP pool queries and optimistic cleartext-password pipelining are disabled, retaining the server-selected PostgreSQL authentication handshake. It always supplies hosted configuration to the existing provider, so fresh inference remains forbidden while owned persisted history and proposal application retain their existing validation. It deliberately skips provider registration and the Node agent's process-start recovery: an isolate starting is not a global server restart. No distributed background-agent execution is implemented. See [Workers deployment](HOSTING.md#cloudflare-workers) for origin, keys, migration, and cutover procedures.

## Accounts and workspace persistence

[auth.ts](apps/server/src/auth.ts) proxies the supported email/password, verification-code, reset, and sign-out endpoints to managed Neon Auth. Accounts and sessions live in Neon's `neon_auth` schema. Each protected request resolves its opaque cookie through the uncached managed session endpoint; a browser header, request body, or JWT decoded without verification never establishes ownership. The proxy preserves refresh/deletion cookies, makes them host-only, and maps secure cookie names for loopback HTTP. Production cookies remain Secure/HttpOnly/SameSite=Lax. Workspaces remain isolated per managed account, without sharing roles.

Failed managed-session lookups retain the public `ACCOUNT_SERVICE_UNAVAILABLE` 503 and emit one sanitized `ACCOUNT_SESSION_LOOKUP_FAILED` event: failure category, upstream status, elapsed time, allowlisted RPC procedure, generated request ID, and serving Worker version (null in Node). `X-Corner-Request-Id` on the failure response correlates the event without cookies, identity data, raw errors, response bodies, or arbitrary request paths. Worker API responses also carry `X-Corner-Version`. No identity cache or Auth validation bypass is introduced.

[database.ts](apps/server/src/database.ts) owns the bounded native `pg` pool for Node/local runtimes and explicit migrations, with certificate/hostname verification for Neon TCP connections. Application traffic uses pooled `DATABASE_URL`; migrations use direct `DATABASE_URL_UNPOOLED`. [queries.ts](apps/server/src/queries.ts) shares Drizzle database/transaction contracts with the request-scoped Worker adapter. [schema.ts](apps/server/src/schema.ts) owns relational workspace metadata/settings, recipes, planned meals, food entries, grocery checks, recipe requests, templates, sessions, exercises, sets, check-ins, training requests/reviews, and scheduled dates; managed Auth and local fixture bookkeeping remain separate. Activity dates are SQL calendar dates. Workout conflict tokens are millisecond-precision timestamp-with-time-zone values decoded to ISO strings. Typed scalar fields support filtering, joins, aggregates, and independent updates; bounded recipe content, template prescriptions, preferences, and review proposals remain JSONB. Live relationships use owner-aware keys/FKs; historical source IDs remain provenance so recorded nutrition/workouts survive source edits or deletion.

Each mutation has a request ID and an original-payload fingerprint computed before domain normalization. One checked-out transaction connection and an owner advisory lock serialize first writes and existing workspaces. [entity-commands.ts](apps/server/src/entity-commands.ts) reads only the addressed records/live dependencies and persists changed entities, revision, retained receipt, and optional agent-application callback atomically. Matching retained retries are checked before revision conflicts, never reapply a command, and return the current bounded revision. Receipt retention remains 1,000 per owner. Food/set/grocery writes do not read or serialize unrelated lifetime collections; set edits retain independent child rows.

[migrate.ts](apps/server/src/migrate.ts) invokes the official Drizzle PostgreSQL migration engine over Kit-generated SQL from `apps/server/migrations`, using direct `DATABASE_URL_UNPOOLED`. A session advisory lock spans metadata setup and the native transaction; strict journal/snapshot/file validation and applied hash/timestamp-prefix checks run before execution. The native `__drizzle_migrations` ledger uses the current application schema, never a shared global test ledger. Its table and owned sequence must be permanent, with the native serial default, primary key, and columns. Migrations are explicitly invoked after a build; application startup only checks the schema. Auth schema lifecycle remains Neon's responsibility. No custom SQL executor, old migration ledger adapter, or legacy SQL archive remains.

Migration `0001_zippy_silver_sable.sql` is an empty-only boundary for ordinary `--apply` runs: in the native migration transaction it locks `workspace_state` exclusively and refuses **any** persisted row before retiring the table. For an explicitly authorized maintenance cutover of populated `0000` workspaces, `preservingDocumentCutover` (CLI `--preserving-cutover --operation-id <id>`, with read-only `--inspect-cutover`) runs under the session migration lock in three resumable phases around unchanged `0001`: (1) preflight-validate every live or unimported archived document and transactionally stage exact raw rows, UTF-8 bytes, revisions, and operation/database/schema/SQL provenance into a dedicated recovery schema (`corner_cutover_recovery`, outside the application catalog) before clearing `workspace_state` and installing a `CHECK (false)` fence; (2) execute the unchanged native Drizzle migrator (`0001`); and (3) transactionally import each archived owner with its original revision and `importRelational` mapping alongside its durable completion marker, refusing any unmarked destination conflict, followed by read-only `validatePersistedRecords`. Once Phase 1 commits, old document code is no longer directly safe because `workspace_state` is empty and fenced; recovery stays in maintenance and resumes forward. Existing SQL/journal/snapshots/native ledger, archived recovery records, and unrelated application/Auth records, keys, backups, and historical receipts are preserved.

`expectedRevision` is optional on ordinary `workspace.mutate` calls and is not sent by the current main workspace mutation path. Do not assume all manual edits have workspace-wide optimistic concurrency checks. Imports require an expected revision and an empty workspace; agent application requires its original base revision. Training mutations also use record-level `expectedUpdatedAt` checks where defined in [workouts.ts](packages/training/src/workouts.ts).

Imports preserve supported historical data rather than matching accounts by email or identity, including older exports without training or scheduled-date markers and orphan historical source IDs. Settings export calls the explicit authenticated server snapshot, not browser state. [workspace-portability.ts](apps/server/src/workspace-portability.ts) reads bounded batches inside one repeatable-read/read-only snapshot; import preview is consistent and commit rechecks emptiness plus expected revision under the owner lock. Transfers have a separate 32 MiB cap and collection/nesting bounds; routine edits have request/record/page/range limits, not the former 1.8 MB lifetime ceiling. Exports exclude credentials, subscription tokens, and separate agent runs. See the [README data guidance](README.md#data-backups-and-upgrades) for full backups and key preservation.

## AI request and application flow

[planning-agent.ts](apps/server/src/planning-agent.ts) owns bounded context, read-only Corner tools, persisted runs, cancellation, structured drafts, and proposal application. Its `InferenceProvider` interface separates planning from [subscription.ts](apps/server/src/subscription.ts), the only implemented inference provider. The browser polls run state; inference is server-side.

```mermaid
sequenceDiagram
    participant U as User / browser
    participant H as Authenticated HTTP routes
    participant A as PlanningAgent
    participant P as SubscriptionProvider
    participant D as Postgres / WorkspaceStore
    U->>H: Request a plan
    H->>A: Start for authenticated owner
    A->>D: Capture bounded context + base revision in one snapshot; persist run
    H-->>U: Accepted run
    A->>P: Infer from bounded Corner context
    P-->>A: Structured result
    A->>D: Save result, not plan changes
    U->>H: Poll and inspect proposal
    H-->>U: Current/proposed changes
    U->>H: Explicit Apply
    H->>A: Apply owned run
    A->>D: Check base revision; atomically commit validated changes, receipt, applied status
    D-->>A: Committed revision
    A-->>H: Applied result
    H-->>U: Revision + run; invalidate affected resource queries
```

[proposalMutations](packages/agent/src/proposals.ts) translates only permitted planning changes into ordinary validated mutations. The agent can propose recipes, meals, future workouts, routines, and targets; it cannot generate intake logs, measurements, or actual workout results. Started, partially recorded, completed, and skipped workouts are protected. These checks belong in server/domain validation, not only in UI copy or model instructions.

Planning context, dependency/detail tools, and history summaries use bounded records or complete date aggregates in consistent snapshots. Tools recheck the original captured revision in short read-only transactions; revision drift fails the request rather than silently rebasing. No database transaction spans inference. Proposal validation accepts addressed dependency records, not a fabricated lifetime `AppState`; application rechecks the original base under the owner lock.


Overlapping Apply requests replay a completed application rather than treating its own committed revision as a stale proposal. Administrative timestamps for proposal mutations use the run's completion time, making their receipt fingerprint deterministic across concurrent requests; activity dates and actual recorded training/food remain user-controlled.

Recipe generation returns a draft; food estimation returns clarification or an editable estimate. Neither saves a recipe or food log automatically. Planning results may also be questions or advice with no mutations.

In the Node runtime, run records persist but background tasks still execute in memory in one process. Startup marks interrupted runs failed rather than resuming them. Agent admission is transactionally serialized so asynchronous SQL does not weaken idempotency or concurrency limits. Shutdown stops new agent work, drains accepted handlers/tasks, and closes the PostgreSQL pool. Keep one Corner Node process; Workers support hosted requests without new inference, not distributed execution of these tasks.

## Credentials and provider availability

Corner sessions and ChatGPT authorization are independent. [subscription.ts](apps/server/src/subscription.ts) owns OAuth state/PKCE/session binding, signed identity checks, encrypted credentials, refresh coordination, model discovery, and disconnect/revocation handling. Short PostgreSQL transactions and generation checks preserve connection/disconnect ordering across awaited I/O. Raw provider credentials never belong in browser state, shared models, or workspace exports. Neon owns account email delivery and managed Auth rate limits; verification uses OTP, and the application verification-policy setting must match the branch.

Credential rotation and catalog/model updates re-read and merge the encrypted registration inside an owner-locked transaction. Identity/generation pins prevent writes across reconnects; token writes additionally pin the refresh token they renewed. OAuth callbacks use one registration/version snapshot and an atomic version check. Provider network I/O stays outside these short transactions.

Local ChatGPT authorization currently requires the supported `http://127.0.0.1` browser origin and local deployment gate. Hosted mode disables this connection and has no alternative inference provider. Do not make hosted AI appear available by changing the deployment label, copying a local grant, hardcoding model access, or silently switching billing paths.

## Verification and release boundaries

[verify.mjs](scripts/verify.mjs) owns conservative local profiles, reusing Turbo, sequential isolated Node server tests, and sequential isolated Vitest web forks. React Testing Library/jsdom exercise production components; Node-environment Vitest covers Vite configuration and service-worker boundaries. Playwright runs the critical browser journeys in Chromium desktop and emulated iPhone WebKit against built web/API outputs, using [browser-test-server.mjs](scripts/browser-test-server.mjs) and the existing disposable PostgreSQL/HTTPS Auth fixture. It owns temporary keys/processes/schema and never reuses a user's development stack. Incomplete or unknown selection never yields a lighter local profile. PR, staging, and main CI always run full verification, including browser journeys. Required checks use ordinary GitHub Actions repository-writer trust, not a workflow-specific GitHub App identity. Live branch protections/default changes require the explicit admin configuration command and exact-tip CI on both persistent branches.

Both persistent branches package the already-built full-stack Worker/assets, maintenance Worker gate, complete immutable Drizzle history, and a self-contained migrator/data validator. [release-artifact.mjs](scripts/release-artifact.mjs) verifies format-4 payloads without executing them, rejecting unsafe configuration, missing/unlisted files, symlinks, traversal, and digest mismatches. Migration prefixes bind SQL, journal entries, and snapshots. The verified tip snapshot classifies storage generation; qualification retains baseline/artifact/native-history/security checks and records `generation`, `previousGeneration`, and `recovery` (`bootstrap`, `forward-only`, `preserving`, or `compatible`). The first document-to-`relational-v1` boundary is **forward repair only** (or `preserving` when explicitly qualified with `--preserving`), never bootstrap and never compatible old-code recovery. Later relational releases retain prior/candidate/recovered read/write and retry qualification against current data. [persisted-records.ts](apps/server/src/persisted-records.ts) validates bounded record batches and session children in one read-only repeatable-read snapshot, never reconstructing a capped lifetime workspace.

The [Worker smoke](scripts/workers-smoke.mjs) tunnels the Neon driver's WebSocket protocol through a fixed-destination, in-process test proxy to its disposable PostgreSQL schema. Auth requests remain restricted to the local HTTPS fixture. It exercises concurrent idempotent writes, owner isolation, rollback after a receipt-write failure, clean candidate pool shutdown, and (under `--preserving`) packaged maintenance-gate isolation and populated document-to-relational conversion, while retaining prior native-pg/candidate/recovery compatibility checks. No cloud database, extra proxy service, or production test binding is involved.

The application is unreleased. Pre-Drizzle artifacts and unpublished REST protocols remain unsupported recovery targets; document-only binaries additionally cannot recover a relational schema. Existing native migration history, audit metadata, and historical receipts remain unchanged and are never relabelled or rewound. Fresh bootstrap, version-pinned adoption of a provisioned Worker, and verified empty schema-only staging baselining remain supported. Schema-only baselining checks the complete current immutable inventory/catalog and empty application/Auth tables before recording verified native identities; it does not stamp legacy/drifted catalogs. Future compatible relational recovery retains current-data, immutable-artifact, ownership, idempotency, and read/write safeguards.

Staging is the review surface; merging to main is release approval. All production modes use `production` without environment reviewers or human-attestation inputs; explicit bootstrap/adoption, preserving cutover/resume, and recovery still require their exact operation and identity pins. Preserving cutovers journal `maintenance-uploaded`, `maintenance-active`, `cutover-validated`, `maintenance-complete`, and (only when database cutover is still `untouched`) `maintenance-aborted` in `production-maintenance`, inspect durable database cutover state before resuming or aborting, and return traffic to the pinned `maintenanceVersionId` if public probes fail after switching to the candidate. Every release completes after automated qualification, live-version verification, and public checks. Both automatic triggers require trusted source merged onto the default branch. Staging's credential-free CI listener dispatches the deployment explicitly on `staging`, so its effectful workflow runs only merged trusted staging source after successful push CI even when GitHub's default branch is `main`; the environment remains staging-only and secrets remain separate. Same-account Cloudflare tokens are **not** hostile-writer isolation. Automated release success does not claim human browser or inbox verification.
