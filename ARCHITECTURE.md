Product apps import compiled subpaths from the owning domain package. Nutrition and training are independent leaf domains; workspace composes their state and mutations. The API contract depends on these contracts without owning their rules. HTTP, storage, account credentials, and external I/O stay server-side.

The workspace shell composes manual feature screens. Authenticated bootstrap loads settings/revision; feature-owned queries load bounded calendars, cursor pages, details, and aggregates. [resources.ts](apps/web/src/features/workspace/resources.ts) composes same-revision dependencies and follows continuations before treating slices as complete. [use-workspace-state.ts](apps/web/src/features/workspace/use-workspace-state.ts) owns preview-local edits, manual mutation serialization, and notifications; live writes never reconstruct lifetime `AppState`. Selected dates, filters, and shared dialogs remain shell state.

Manual profile/targets, recipe, food-log, and meal-picker editors use direct TanStack Form fields with mount-time defaults and awaited save promises. Form values own editable drafts; stable record IDs/timestamps and navigation/search state remain outside them. Shared UI controls and native browser constraints retain their existing presentation and timing. Settings are explicitly parsed before saving, and recipe ingredient normalization preserves matching shopping metadata. Workspace mutation serialization and notifications remain owned by the existing save orchestration; failed saves retain editable values.

The product uses React Router with Today (`/`), `/workouts`, `/planner`, `/recipes`, `/groceries`, and `/settings`. Unknown paths, including retired `/agent` and `/studio`, replace history with `/`. Session loading preserves the requested destination. Settings owns optional profile editing and previewed empty-workspace import. Password-reset links retain `/account/reset-password` and replace sensitive queries after validation. Storybook owns catalog history and canonical `?path=/story/<group-lowercase>--<id>` links; shared UI accepts rendered links instead of importing a router.

[theme.tsx](apps/web/src/theme.tsx) owns the product's browser-local Light/Dark/System preference, resolves live system changes, and aligns the document's `data-corner-theme`, `.dark` class, and browser theme-color metadata. `ThemeProvider` wraps account entry and the workspace. Shared `ThemePicker` and optional `AppSidebar.theme` remain controlled UI; they do not access storage or workspace data. The catalog bridges its independent Storybook theme global through `src/catalog-theme.ts` and resolves it in its preview provider.

Neon is managed infrastructure, not another deployable application. Root [neon.ts](neon.ts) configures Auth and branch policy; database access, the managed Auth proxy, and application SQL migrations remain owned by `apps/server`. There is no separate Neon app or database package.

## Runtime and origin boundary

Development runs product Vite on `3000`, API on loopback `3001`, nutrition/training/workspace/API watchers, and the independent design catalog on `3002`. Vite proxies `/api` and rejects retired `/auth/callback` through the server rather than serving SPA HTML. Turbo builds domain/API dependencies before consumers.

The `pnpm run dev` controller in [scripts/local-dev.mjs](scripts/local-dev.mjs) always isolates development from cloud Neon. [compose.local.yaml](deployment/compose.local.yaml) supplies owned PostgreSQL 17; [local-runtime.mjs](apps/server/scripts/local-runtime.mjs) starts a persistent HTTPS Better Auth fixture after explicit application migrations. Native `pg` remains unchanged. Controller and child environments are scrubbed; no development entrypoint loads root environment files. API development requires local mode and loopback database/Auth endpoints, rejecting database host overrides before connections or private-key writes. The controller runs the existing Turbo API/web/catalog/compiler tasks; optional loopback port selection changes the browser/API/catalog together.

The explicit seed operation reaches only a private Unix controller socket. It verifies Compose container/volume ownership and database identity before preparing the local runtime. [local-services.mjs](apps/server/scripts/local-services.mjs) reserves deterministic fixture account IDs and seed dates in development-only bookkeeping tables, creates accounts through Better Auth, and imports synthetic workspaces through authenticated native RPC. Durable completion records preserve edited fixtures beyond bounded mutation-receipt retention. The local fixture's Auth tables share its private database schema; hosted `neon_auth` lifecycle remains Neon's responsibility. No seed code is part of application migrations, Worker entrypoints, or release hooks; no staging/production seed target exists.

Local shutdown retains database records and `.corner-local/` keys. Explicit reset validates ownership before deleting only its database volume. The ignored private directory is also excluded from Docker contexts; existing `data/`, environment files, and hosted secrets remain untouched. The fixture supplies no mail delivery or AI credentials and does not establish managed Neon Auth parity.

[local-migrations.ts](apps/server/src/local-migrations.ts) handles the owned local database's transition to native Drizzle history before invoking the ordinary migrator. Under the migration lock, it checks the local installation identity and validates existing application definitions against an isolated schema created from the initial checked-in Drizzle SQL. A matching pre-Drizzle database with its old audit ledger and absent/empty native history receives only a native baseline entry; application/Auth records, seed state, and historical audit metadata remain untouched. Temporary reference DDL and baseline writes are transactional. This path is not used by hosted startup, deployment migrations, or staging provisioning.

Production runs compiled JavaScript from `apps/server/dist`; the same Node process serves `apps/web/dist` and API routes on one origin. It runs neither Vite nor a TypeScript loader. The hosted template adds Caddy in front of this process, not a second application backend.

Both runtimes call the same Hono application's `fetch` handler for native oRPC and MCP resources. The shared `@packages/api` contract defines account/workspace procedures under `/api/rpc`; browser calls use native oRPC and TanStack Query. Native requests carry `{json: input}`, successes `{json: output}`, and errors `{json: {defined, code, status, message, data}}`. Session ownership, exact Origin, procedure-specific streaming body limits, renewal cookies, and no-store apply to successes and failures. Managed Auth `/api/auth`, `GET /api/health`, delegated authorization, and `/mcp` retain separate protocols; retired `/auth/callback` returns no-store 404.

The transport authenticates the original Request and never normalizes a mutation before fingerprinting. Node's upload bridge permits native errors before closing rejected unread uploads. Browser read-only workspace queries retry only `ACCOUNT_SERVICE_UNAVAILABLE`, twice after 500/1,000 ms; mutations and account queries do not automatically retry. Cancellation stops backoff on session invalidation. Revision floors reject stale pre-write reads; logout clears private query/mutation caches. Editable drafts and filters remain local.

The [web manifest](apps/web/public/manifest.webmanifest) and Apple Home Screen metadata provide standalone installation on the same origin. [pwa.ts](apps/web/src/pwa.ts) registers the root-scoped [service worker](apps/web/public/sw.js) only in production builds, after page load. It handles same-origin GET document navigations with network-only fetches and a self-contained, no-store offline recovery response; API, Auth, account-recovery, non-navigation, and write requests remain untouched. It uses no Cache Storage, offline mutation queue, or forced worker activation/reload, so installation adds no persistent private-data cache or stale-shell fallback. Both runtimes serve these public assets through their existing static security boundary; Node explicitly supplies the manifest MIME type.

[config.ts](apps/server/src/config.ts) resolves data paths from the repository root, independent of workspace working directory. [index.ts](apps/server/src/index.ts) validates the canonical Host; account and workspace writes also require the configured origin. [request-identity.ts](apps/server/src/request-identity.ts) accepts forwarded client identity only with the configured proxy proof. Preserve these boundaries when changing the proxy or callback path; do not trust arbitrary forwarding headers. Deployment details remain in [HOSTING.md](HOSTING.md#proxy-boundary).

Cloudflare Workers bundle the same assets and native Fetch entrypoint. All requests pass canonical-origin, no-store, and security middleware before asset serving. [runtime-config.ts](apps/server/src/runtime-config.ts) validates DB/Auth/config inputs; Node [config.ts](apps/server/src/config.ts) only resolves repository data paths and calls that pure loader. Neither reads, creates, or replaces private configuration or model keys.

Production is one full-stack Worker named `corner`, using [apps/server/src/worker.ts](apps/server/src/worker.ts) for assets, API, and callbacks, plus the packaged [apps/server/src/maintenance-worker.ts](apps/server/src/maintenance-worker.ts) gate (`worker/maintenance-worker.js`) for explicit operator-driven maintenance cutovers. There is no frontend Worker or service binding. One immutable format-4 artifact supplies `wrangler.json`, `worker/worker.js`, `worker/maintenance-worker.js`, assets, Drizzle SQL/journal/snapshots, and `migration/dist/migrate.mjs` to production and staging without rebuilding. The packaged configuration names `corner`, binds `ASSETS` and `CF_VERSION_METADATA`, disables `workers_dev`, and enables `preview_urls`. Production enables `workers_dev` only for its exact stable `https://corner.<account-subdomain>.workers.dev` origin; HTTPS custom-domain production keeps it disabled. Initial expected production origin is `https://corner.adam-nathaniel-woo.workers.dev`. Deployment/Preview URLs are not production canonical origins. Independent Cloudflare Builds remain disabled.
Staging is one [native Cloudflare Preview](https://developers.cloudflare.com/workers/previews/) named `staging` under `corner`; an operator-provisioned parent can host staging before its first production application release. It consumes the identical full-stack payload with explicitly isolated staging database/Auth/keys. Expected stable origin is `https://staging-corner.adam-nathaniel-woo.workers.dev`; preview-only Access must protect that exact hostname and deployment URLs while production stays outside Access. Keep top-level `preview_urls` enabled. Native Preview configuration, not aliased Version URLs or service bindings, supplies resource isolation. Its existing schema-only Neon branch retains synthetic records and keys across merges and has no expiry. [staging-baseline.ts](apps/server/src/staging-baseline.ts) verifies an empty initial copied schema against read-only source metadata and checked-in Drizzle SQL before writing only native migration history; it is not a routine reset of populated staging. No per-feature app/database previews or production fallback exist. Never recreate removed legacy Workers. The first tracked production release can explicitly adopt the current provisioned version, pinned before migration and deployment; this creates no fictitious qualified history. Automated qualification, live-version verification, and public checks gate production's one-version format-4 `corner-production` receipt; staging uses its separate format-4 `corner-staging-preview` ledger after successful exact current trusted staging push CI. These are implementation contracts, not evidence of live cutover. See [staging setup](HOSTING.md#persistent-staging-database-and-auth).

Main's native repository ruleset requires a successful `staging` environment deployment as well as full CI before merge, with no bypass actors and no deployment rule on staging itself. Preview migration and deployed journals carry terminal success/failure statuses; only verified completion records a successful serving deployment. Production and Preview share `release.mjs`'s bounded public verifier: up to 12 health/version attempts five seconds apart for the exact uploaded version, followed by security assertions that are never retried. Only public readiness is retried, not schema or traffic effects. A pinned staging completion operation verifies immutable artifact/configuration, current schema/serving journals, live bindings, and public behavior without migration, upload, or production traffic changes.

The Worker creates/closes one Neon WebSocket pool per API/delegation request through [worker-database.ts](apps/server/src/worker-database.ts), never caching connections across isolates. Drizzle's `neon-serverless` adapter preserves interactive transactions on one connection. HTTP pool queries and optimistic cleartext-password pipelining remain disabled. No model-provider registration, inference, task recovery, or background-agent lifecycle remains.

## Accounts and workspace persistence

[auth.ts](apps/server/src/auth.ts) proxies the supported email/password, verification-code, reset, and sign-out endpoints to managed Neon Auth. Accounts and sessions live in Neon's `neon_auth` schema. Each protected request resolves its opaque cookie through the uncached managed session endpoint; a browser header, request body, or JWT decoded without verification never establishes ownership. The proxy preserves refresh/deletion cookies, makes them host-only, and maps secure cookie names for loopback HTTP. Production cookies remain Secure/HttpOnly/SameSite=Lax. Workspaces remain isolated per managed account, without sharing roles.

Failed managed-session lookups retain the public `ACCOUNT_SERVICE_UNAVAILABLE` 503 and emit one sanitized `ACCOUNT_SESSION_LOOKUP_FAILED` event: failure category, upstream status, elapsed time, allowlisted RPC procedure, generated request ID, and serving Worker version (null in Node). `X-Corner-Request-Id` on the failure response correlates the event without cookies, identity data, raw errors, response bodies, or arbitrary request paths. Worker API responses also carry `X-Corner-Version`. No identity cache or Auth validation bypass is introduced.

[database.ts](apps/server/src/database.ts) owns the bounded native `pg` pool for Node/local runtimes and explicit migrations, with certificate/hostname verification for Neon TCP connections. Application traffic uses pooled `DATABASE_URL`; migrations use direct `DATABASE_URL_UNPOOLED`. [queries.ts](apps/server/src/queries.ts) shares Drizzle database/transaction contracts with the request-scoped Worker adapter. [schema.ts](apps/server/src/schema.ts) owns relational workspace metadata/settings, recipes, planned meals, food entries, grocery checks, recipe requests, templates, sessions, exercises, sets, check-ins, training requests/reviews, and scheduled dates; managed Auth and local fixture bookkeeping remain separate. Activity dates are SQL calendar dates. Workout conflict tokens are millisecond-precision timestamp-with-time-zone values decoded to ISO strings. Typed scalar fields support filtering, joins, aggregates, and independent updates; bounded recipe content, template prescriptions, preferences, and review proposals remain JSONB. Live relationships use owner-aware keys/FKs; historical source IDs remain provenance so recorded nutrition/workouts survive source edits or deletion.

Each mutation has a request ID and an original-payload fingerprint computed before normalization. One transaction connection and owner advisory lock serialize writes. [entity-commands.ts](apps/server/src/entity-commands.ts) persists addressed changes, revision, and retained receipt atomically. Matching retained retries never reapply commands; retired commands are rejected before receipt replay. Receipt retention remains 1,000 per owner. Food/set/grocery writes do not serialize unrelated lifetime collections; set edits retain independent child rows.

[migrate.ts](apps/server/src/migrate.ts) invokes the official Drizzle PostgreSQL migration engine over Kit-generated SQL from `apps/server/migrations`, using direct `DATABASE_URL_UNPOOLED`. A session advisory lock spans metadata setup and the native transaction; strict journal/snapshot/file validation and applied hash/timestamp-prefix checks run before execution. The native `__drizzle_migrations` ledger uses the current application schema, never a shared global test ledger. Its table and owned sequence must be permanent, with the native serial default, primary key, and columns. Migrations are explicitly invoked after a build; application startup only checks the schema. Auth schema lifecycle remains Neon's responsibility. No custom SQL executor, old migration ledger adapter, or legacy SQL archive remains.

Migration `0001_zippy_silver_sable.sql` is an empty-only boundary for ordinary `--apply` runs: in the native migration transaction it locks `workspace_state` exclusively and refuses **any** persisted row before retiring the table. For an explicitly authorized maintenance cutover of populated `0000` workspaces, `preservingDocumentCutover` (CLI `--preserving-cutover --operation-id <id>`, with read-only `--inspect-cutover`) runs under the session migration lock in three resumable phases around unchanged `0001`: (1) preflight-validate every live or unimported archived document and transactionally stage exact raw rows, UTF-8 bytes, revisions, and operation/database/schema/SQL provenance into a dedicated recovery schema (`corner_cutover_recovery`, outside the application catalog) before clearing `workspace_state` and installing a `CHECK (false)` fence; (2) execute the unchanged native Drizzle migrator (`0001`); and (3) transactionally import each archived owner with its original revision and `importRelational` mapping alongside its durable completion marker, refusing any unmarked destination conflict, followed by read-only `validatePersistedRecords`. Once Phase 1 commits, old document code is no longer directly safe because `workspace_state` is empty and fenced; recovery stays in maintenance and resumes forward. Existing SQL/journal/snapshots/native ledger, archived recovery records, and unrelated application/Auth records, keys, backups, and historical receipts are preserved.

`expectedRevision` is optional on ordinary `workspace.mutate` calls and absent from the main manual mutation path. Imports require an expected revision and empty workspace. Training mutations retain record-level `expectedUpdatedAt` checks where defined in [workouts.ts](packages/training/src/workouts.ts).

Imports preserve supported historical data rather than matching accounts by email or identity, including older exports without training or scheduled-date markers and orphan historical source IDs. Settings export calls the explicit authenticated server snapshot, not browser state. [workspace-portability.ts](apps/server/src/workspace-portability.ts) reads bounded batches inside one repeatable-read/read-only snapshot; import preview is consistent and commit rechecks emptiness plus expected revision under the owner lock. Transfers have a separate 32 MiB cap and collection/nesting bounds; routine edits have request/record/page/range limits, not the former 1.8 MB lifetime ceiling. Exports exclude credentials, subscription tokens, and separate agent runs. See the [README data guidance](README.md#data-backups-and-upgrades) for full backups and key preservation.

Historical recipe requests remain validated archive data for workspace import/export and retained relational storage. They are not active studio requests: `request.save` and `request.fulfill` are no longer accepted mutation commands, including retained-receipt retries. Removing their executable paths does not delete archived requests, tables, or applied migrations.

## Delegated MCP connections

[delegation.ts](apps/server/src/delegation.ts) configures maintained `oidc-provider` `9.13.2`; [delegation-storage.ts](apps/server/src/delegation-storage.ts) implements its supported adapter against existing Drizzle/PostgreSQL. Neon Auth remains the only browser identity authority. Authorization, consent and resume validate its fresh uncached principal before opening a transaction. Insert-only interaction provenance binds the exact managed owner/session ID and actual verified expiry; issuer cookies cannot substitute for that identity check. Consent and connections reuse shared Base UI controls.

OAuth discovery/DCR/authorization/token/revocation/JWKS are separate from browser oRPC and stateless SDK Streamable HTTP `/mcp`. Code clients require S256 PKCE; audience is exactly the configured origin's `/mcp`. `mcp.ts` validates an opaque maintained access-token model plus live owner/client-bound Grant on every request, then registers only granted implemented tools from `mcp-reads.ts`, `mcp-writes.ts` and `mcp-training.ts`. Caller-selected owners/resources, browser cookies and query credentials do not authenticate MCP. Supplied Origins must exactly match the configured origin; bearer clients need no browser session. Delegated writes cover dated meal-plan create/edit, food-log/recipe CRUD, routine create/edit, atomic unstarted workout planning and separately scoped existing-history corrections. Retired request/review executors, plan/history deletion and workout start/completion tools remain unavailable.

Transactions lock only the affected grant and re-read credentials after obtaining that lock. Documented issuer error/revocation events distinguish ordinary rollback from maintained replay-family revocation; HTTP status/error strings never drive protocol transitions. Supported `provider.use` middleware commits before Koa emits credential headers; documented `interactionResult` persists consent without prematurely ending the response. Owner revocation deletes that grant and its tokens atomically under the same lock. New consent creates a new grant generation. Managed-session I/O precedes locks; remote client-metadata/JWKS/sector fetches, PAR, DPoP and issuer identity/logout/userinfo endpoints are disabled rather than advertised without implementation.

Connections explicitly permit ongoing selected access after browser sign-out. Access tokens last five minutes; grant/refresh maximum lifetime is thirty days. Revocation denies subsequent requests, not an operation already authenticated before the revocation transaction. Reads reuse existing bounded domain/store queries, scopes and revision/cursor semantics; the catalog and limits are in [README.md](README.md#owner-approved-mcp-connections). Planned and recorded activity remain distinct.

`meal-plans:write` independently grants `edit_meal_plans`: explicit create/patch members, at most 100, applied autonomously without per-change approval. `WorkspaceStore.delegatedWrite` reuses the existing owner-locked commit transaction and receipt retention. Scope checks precede replay; operation IDs are hashed with validated client/grant IDs. A per-request closure in `mcp.ts` preserves original JSON arguments before SDK/domain normalization for the semantic fingerprint. Exact retained retries return the receipt's committed revision, even after later changes; changed original payloads conflict before stale-revision checks. New writes require `expectedRevision`, with no silent rebase. Existence checks, patch merges, recipe validation, all batch members, revision and receipt share the transaction. Responses contain only revision; manual mutation semantics and receipt replay remain unchanged.

`recipes:write` and `food-logs:write` grant explicit create/update tools; `recipes:delete` and `food-logs:delete` independently grant deletes. All use the same guarded transaction, explicit create-versus-existing checks, locked patch merge and revision-only responses. Create inputs supply complete record fields; no write implicitly copies ungranted recipe content into food logs or returns existing records. Nutrition patches preserve omitted nutrient values; optional links/recipe metadata can be removed with explicit null. Existing `executeEntityCommand`/food validators enforce recipe-in-use rejection, one-log-per-plan uniqueness and owner-scoped live references while allowing unchanged historical links. Recipe edits/deletion never rewrite or cascade historical food snapshots. Manual mutation semantics remain unchanged.

Nutrition edit/delete grants and `routines:write` also expose `get_workspace_revision`: owner-scoped metadata returning only the current revision, never settings or records. Mutation-only clients can discover a nonzero starting revision or recover after a conflict by explicitly reviewing and resubmitting with a new operation ID. Discovery does not reserve a revision, bypass expected-revision checks, or silently rebase writes.

`mcp-training.ts` composes the same per-request original-arguments resolver and qualified `WorkspaceStore.delegatedWrite` transaction, not a second mutation framework. `routines:write` grants explicit create/patch without cascading snapshot rewrites. `workout-plans:write` grants atomic batches of up to 100 explicit planned records; authoritative lifecycle, recorded actuals and readiness are checked under the owner lock. Plan exercises accept targets only, never actual sets. `workout-history:write` independently corrects existing non-planned outcomes or records with actuals/readiness, including skipped and imported planned-with-actuals, while preserving lifecycle exactly. It cannot create history or change status. Both session update paths require the actual nonnullable `expectedUpdatedAt` in addition to workspace revision; native training command validation still advances saved versions and preserves creation timestamps. Missing updates fail, supplied collections replace wholesale, omitted fields survive locked merges, and responses contain revision only. Explicit field schemas prohibit copying ungranted routine contents or changing immutable/lifecycle fields.

Additive migration `0002_delegated_access.sql` creates `delegation_objects` (maintained protocol payloads and app consent provenance) and `delegation_issuer` (insert-once cookie secret/private signing JWK). These are neither managed account/session mirrors nor workspace portability fields. Initialization is transactional on first OAuth use, not a startup environment/secret requirement. Retain them in installation backups; never expose private keys or credentials in APIs, exports, assets, logs, or browser storage, or reuse retired provider keys.

Either session write scope independently exposes `get_workout_versions` in `mcp-reads.ts`. It reuses `consistentRead` for an owner-scoped repeatable-read snapshot of workspace revision and only addressed session IDs/update timestamps (at most 25), never domain contents or an ID listing. This supports create-then-edit and recovery after manual writes without an implicit `workouts:read` dependency; both mutation concurrency checks remain mandatory.
Node mounts the maintained native callback on its existing listener. The same Worker uses documented `cloudflare:node`/`node:http` adaptation, native `createRequire` for maintained CommonJS built-ins and Wrangler's standard `nodejs_compat` builtin resolution without application aliases. It adds no process, real listener, service binding or alternative persistence. The issuer's unsupported-Worker warning stays visible; observed disposable compatibility does not imply vendor support or final canonical bundle qualification. OAuth documents/protocols are no-store; Vite routes protocol endpoints separately from consent/sign-in SPA routes, and the service worker excludes OAuth/MCP/discovery.

## Retired assistance and historical data

All AI/agent RPC namespaces, retired `/auth/callback`, model-provider/inference/task/recovery code, and active recipe/training request/review commands are removed. The separate delegated-access issuer does not restore them. There is no compatibility executor or replacement history screen. Manual recipes, meals, groceries, food logs, workouts, routines, actual sets, check-ins, progress, profile/account settings, and import/export remain.

Historical recipe requests and training requests/reviews remain validated serialized workspace archive data. Existing AI-run/provider tables, applied migrations, receipts, encrypted provider records, original private configuration, keys, and backups are retained. Separate provider/run installation archives are not new workspace JSON fields and cannot become executable through imports or receipt retries.

Application Config requires DB/Auth inputs, not `authSecret` or `tokenEncryptionKey`. The local controller's independent Auth/password/control secrets and TLS keys remain required and preserved. Before final retirement release, the operator must separately confirm backups and revoke any existing ChatGPT grants; source removal neither proves revocation nor authorizes live deletion or rotation.

## Verification and release boundaries

[verify.mjs](scripts/verify.mjs) owns conservative local profiles, reusing Turbo, sequential isolated Node server tests, and sequential isolated Vitest web forks. React Testing Library/jsdom exercise production components; Node-environment Vitest covers Vite configuration and service-worker boundaries. Playwright runs the critical browser journeys in Chromium desktop and emulated iPhone WebKit against built web/API outputs, using [browser-test-server.mjs](scripts/browser-test-server.mjs) and the existing disposable PostgreSQL/HTTPS Auth fixture. It owns temporary keys/processes/schema and never reuses a user's development stack. Incomplete or unknown selection never yields a lighter local profile. PR, staging, and main CI always run full verification, including browser journeys. Required checks use ordinary GitHub Actions repository-writer trust, not a workflow-specific GitHub App identity. Live branch protections/default changes require the explicit admin configuration command and exact-tip CI on both persistent branches.

Both persistent branches package the already-built full-stack Worker/assets, maintenance Worker gate, complete immutable Drizzle history, and a self-contained migrator/data validator. [release-artifact.mjs](scripts/release-artifact.mjs) verifies format-4 payloads without executing them, rejecting unsafe configuration, missing/unlisted files, symlinks, traversal, and digest mismatches. Migration prefixes bind SQL, journal entries, and snapshots. The verified tip snapshot classifies storage generation; qualification retains baseline/artifact/native-history/security checks and records `generation`, `previousGeneration`, and `recovery` (`bootstrap`, `forward-only`, `preserving`, or `compatible`).
