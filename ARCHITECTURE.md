# Architecture

This describes the implemented architecture and the boundaries a change must preserve. Product direction is in [PRODUCT.md](PRODUCT.md), visual/interaction guidance in [DESIGN.md](DESIGN.md), and working commands in [AGENTS.md](AGENTS.md). [README.md](README.md) owns first use; [HOSTING.md](HOSTING.md) owns deployment and backup procedures.

## Where changes belong

The product apps depend on `@packages/shared/<module>` through its compiled package exports. Shared domain code does not own HTTP, storage, account credentials, or provider calls. Server I/O stays server-side; web components render state and send authenticated requests. The workspace map is the current allocation of responsibilities, not a prohibition on a justified future topology change.

The workspace shell composes feature screens from `apps/web/src/features`: `today`, `meal-planner`, `recipes`, `groceries`, `recipe-studio`, `food-log`, and `settings`. Each feature owns its screen, forms, and feature-specific calculations or request logic. Existing training and agent panels remain in their current modules. [use-workspace-state.ts](apps/web/src/features/workspace/use-workspace-state.ts) consumes the canonical workspace query and owns preview-local edits, mutation serialization, and notifications; [workspace-overlays.tsx](apps/web/src/features/workspace/workspace-overlays.tsx) coordinates dialogs used across screens. The shell retains the shared selected date and calls the recipe-filter and studio hooks unconditionally so their filters, drafts, and generation request identity survive route changes. Feature UI continues to compose `@packages/ui` primitives; the extracted workspace UI helpers preserve the existing app-specific compositions.

Both browser apps use React Router in declarative mode, with a `BrowserRouter` at each entrypoint. The product's route table in `corner-app.tsx` selects Today (`/`), `/agent`, `/workouts`, `/planner`, `/recipes`, `/groceries`, `/studio`, and `/settings`; workspace state stays mounted across these routes. Unknown workspace paths replace the current history entry with `/`. Session loading gates workspace access without discarding a requested destination; new accounts need no onboarding or completed profile. Settings owns optional profile editing and the previewed, empty-workspace import in [import-workspace.tsx](apps/web/src/import-workspace.tsx). Password-reset links retain their fixed `/account/reset-password` path, validate the token before consumption, and replace the sensitive query through the router. The catalog uses router search parameters for its existing `?component=` links. Shared UI components accept rendered links rather than importing a router; apps supply React Router `Link` elements.

Neon is managed infrastructure, not another deployable application. Root [neon.ts](neon.ts) configures Auth and branch policy; database access, the managed Auth proxy, and application SQL migrations remain owned by `apps/server`. There is no separate Neon app or database package.

## Runtime and origin boundary

Development runs product Vite on browser port `3000`, the API on loopback port `3001`, shared/API-package compiler watchers, and the independent design catalog on `3002`. [vite.config.ts](apps/web/vite.config.ts) proxies `/api` and `/auth/callback` without rewriting the canonical browser Host/Origin. Turbo builds shared/API dependencies before consumers; see [turbo.json](turbo.json).

The `pnpm run dev` controller in [scripts/local-dev.mjs](scripts/local-dev.mjs) always isolates development from cloud Neon. [compose.local.yaml](deployment/compose.local.yaml) supplies owned PostgreSQL 17; [local-runtime.mjs](apps/server/scripts/local-runtime.mjs) starts a persistent HTTPS Better Auth fixture after explicit application migrations. Native `pg` remains unchanged. Controller and child environments are scrubbed; no development entrypoint loads root environment files. API development requires local mode and loopback database/Auth endpoints, rejecting database host overrides before connections or private-key writes. The controller runs the existing Turbo API/web/catalog/compiler tasks; optional loopback port selection changes the browser/API/catalog together.

The explicit seed operation reaches only a private Unix controller socket. It verifies Compose container/volume ownership and database identity before preparing the local runtime. [local-services.mjs](apps/server/scripts/local-services.mjs) reserves deterministic fixture account IDs and seed dates in development-only bookkeeping tables, creates accounts through Better Auth, and imports synthetic workspaces through authenticated native RPC. Durable completion records preserve edited fixtures beyond bounded mutation-receipt retention. The local fixture's Auth tables share its private database schema; hosted `neon_auth` lifecycle remains Neon's responsibility. No seed code is part of application migrations, Worker entrypoints, or release hooks; no staging/production seed target exists.

Local shutdown retains database records and `.corner-local/` keys. Explicit reset validates ownership before deleting only its database volume. The ignored private directory is also excluded from Docker contexts; existing `data/`, environment files, and hosted secrets remain untouched. The fixture supplies no mail delivery or AI credentials and does not establish managed Neon Auth parity.

Production runs compiled JavaScript from `apps/server/dist`; the same Node process serves `apps/web/dist` and API routes on one origin. It runs neither Vite nor a TypeScript loader. The hosted template adds Caddy in front of this process, not a second application backend.

Both runtime entrypoints call the same Hono app's `fetch` handler. Native oRPC procedures under `/api/rpc` replace all handwritten application REST routes. The shared `@packages/api` contract defines account, workspace, AI, and agent procedures; browser calls use an oRPC client and TanStack Query server-state cache. Native requests carry `{json: input}`, successes `{json: output}`, and errors `{json: {defined, code, status, message, data}}`; `SIGN_IN_REQUIRED` and `CORNER_ERROR` (with `data.code`) retain application error semantics. Session ownership, canonical Origin, procedure-specific body limits, and renewal cookies apply to RPC successes and failures. Managed Auth `/api/auth`, OAuth `/auth/callback`, and `GET /api/health` stay outside oRPC.

[rpc.ts](apps/server/src/rpc.ts) authenticates the original Request, enforces exact Origin and procedure-specific streaming JSON limits, then passes the parsed envelope to oRPC's public standard adapter. Managed Auth and OAuth still receive the original session context; the transport never normalizes a mutation before the store fingerprints it. Node's upload bridge permits a native error response before closing rejected, unread uploads rather than poisoning a reusable HTTP connection.

[rpc.ts](apps/web/src/rpc.ts) owns the browser QueryClient, native client, private session-lifetime keys, and monotonic workspace hydration. Feature hooks use queries and mutations without automatic retries; drafts, filters, and preview edits remain local. Writes cancel pending workspace reads and accept full authoritative responses without rolling back a newer revision. Logout and expiration clear private query and mutation caches; mounted mutation functions and late completions reject retired lifetimes, including a later login by the same account. Workspace reads refresh on visible focus/reconnect. Provider connection reads do not refetch on focus/reconnect. Active agent runs poll every two seconds, including in the background, and stop when terminal.

[config.ts](apps/server/src/config.ts) resolves data paths from the repository root, independent of workspace working directory. [index.ts](apps/server/src/index.ts) validates the canonical Host; account and workspace writes also require the configured origin. [request-identity.ts](apps/server/src/request-identity.ts) accepts forwarded client identity only with the configured proxy proof. Preserve these boundaries when changing the proxy or callback path; do not trust arbitrary forwarding headers. Deployment details remain in [HOSTING.md](HOSTING.md#proxy-boundary).

Cloudflare Workers use [wrangler.jsonc](apps/server/wrangler.jsonc) to bundle the same web assets and a native Fetch entrypoint. All requests run through the Worker before asset serving, preserving canonical-origin checks, API no-store policy, static security headers, and account-reset deep links. [runtime-config.ts](apps/server/src/runtime-config.ts) validates both runtimes; the Node-only [config.ts](apps/server/src/config.ts) adapter resolves repository paths and generates/reads keys only when explicit secrets are absent. Workers require explicit secret bindings and never import that filesystem adapter at runtime.

Production is one full-stack Worker named `corner`, using [apps/server/src/worker.ts](apps/server/src/worker.ts) for assets, API, and callbacks. There is no frontend Worker or service binding. One immutable format-3 artifact supplies `wrangler.json`, `worker/worker.js`, assets, checksummed migrations, and `migration/dist/migrate.mjs` to production and staging without rebuilding. The packaged configuration names `corner`, binds `ASSETS` and `CF_VERSION_METADATA`, disables `workers_dev`, and enables `preview_urls`. Production enables `workers_dev` only for its exact stable `https://corner.<account-subdomain>.workers.dev` origin; HTTPS custom-domain production keeps it disabled. Initial expected production origin is `https://corner.adam-nathaniel-woo.workers.dev`. Deployment/Preview URLs are not production canonical origins. Independent Cloudflare Builds remain disabled.

Staging is one [native Cloudflare Preview](https://developers.cloudflare.com/workers/previews/) named `staging` under `corner`; an operator-provisioned parent can host staging before its first production application release. It consumes the identical full-stack payload with explicitly isolated staging database/Auth/keys. Expected stable origin is `https://staging-corner.adam-nathaniel-woo.workers.dev`; preview-only Access must protect that exact hostname and deployment URLs while production stays outside Access. Keep top-level `preview_urls` enabled. Native Preview configuration, not aliased Version URLs or service bindings, supplies resource isolation. Its existing schema-only Neon branch retains synthetic records and keys across merges and has no expiry. [staging-baseline.ts](apps/server/src/staging-baseline.ts) verifies an empty initial copied schema against read-only source metadata and checked-in SQL before writing only migration history; it is not a routine reset of populated staging. No per-feature app/database previews or production fallback exist. Never recreate removed legacy Workers. The first tracked production release can explicitly adopt the current provisioned version, pinned before migration and deployment; this creates no fictitious qualified history. Protected human approval gates production's one-version format-3 `corner-production` receipt; staging uses its separate `corner-staging-preview` ledger after successful exact current trusted staging push CI. These are implementation contracts, not evidence of live cutover. See [staging setup](HOSTING.md#persistent-staging-database-and-auth).

The Worker creates/closes one PostgreSQL pool within each API request; sockets are never cached across isolates/requests. It always supplies hosted configuration to the existing provider, so fresh inference remains forbidden while owned persisted history and proposal application retain their existing validation. It deliberately skips provider registration and the Node agent's process-start recovery: an isolate starting is not a global server restart. No distributed background-agent execution is implemented. See [Workers deployment](HOSTING.md#cloudflare-workers) for origin, keys, migration, and cutover procedures.

## Accounts and workspace persistence

[auth.ts](apps/server/src/auth.ts) proxies the supported email/password, verification-code, reset, and sign-out endpoints to managed Neon Auth. Accounts and sessions live in Neon's `neon_auth` schema. Each protected request resolves its opaque cookie through the uncached managed session endpoint; a browser header, request body, or JWT decoded without verification never establishes ownership. The proxy preserves refresh/deletion cookies, makes them host-only, and maps secure cookie names for loopback HTTP. Production cookies remain Secure/HttpOnly/SameSite=Lax. Workspaces remain isolated per managed account, without sharing roles.

[database.ts](apps/server/src/database.ts) owns one bounded `pg` pool using the pooled `DATABASE_URL`, with certificate/hostname verification for Neon connections. [store.ts](apps/server/src/store.ts) stores one serialized document per owner in `workspace_state`, with an integer revision. Mutation receipts, agent runs, and encrypted provider records are separate PostgreSQL tables. State validation retains collection limits and a `1_800_000`-byte serialized bound.

Each mutation has a request ID. On one checked-out connection, `BEGIN` plus an owner-scoped transaction advisory lock serializes first writes and existing workspaces. The store checks payload fingerprints, validates the resulting state, advances its revision, and commits state and receipt together. Matching retained retries do not reapply changes; reusing an ID for a different payload is rejected. Receipt retention remains bounded.

[migrate.ts](apps/server/src/migrate.ts) applies ordered, checksummed SQL from `apps/server/migrations` through `DATABASE_URL_UNPOOLED`. Migrations are explicitly invoked after a build, transactional, and serialized; application startup only checks the schema. Auth schema lifecycle is Neon's responsibility. No SQLite runtime or app-owned mail adapter remains.

`expectedRevision` is optional on ordinary `workspace.mutate` calls and is not sent by the current main workspace mutation path. Do not assume all manual edits have workspace-wide optimistic concurrency checks. Imports require an expected revision and an empty workspace; agent application requires its original base revision. Training mutations also use record-level `expectedUpdatedAt` checks where defined in [training.ts](packages/shared/src/training.ts).

Imports preserve supported historical data rather than matching accounts by email or identity. Exported workspace data excludes account credentials, subscription tokens, and separate agent runs. See the [README data guidance](README.md#data-backups-and-upgrades) for complete backups and key preservation.

## AI request and application flow

[planning-agent.ts](apps/server/src/planning-agent.ts) owns bounded context, read-only Corner tools, persisted runs, cancellation, structured drafts, and proposal application. Its `InferenceProvider` interface separates planning from [subscription.ts](apps/server/src/subscription.ts), the only implemented inference provider. The browser polls run state; inference is server-side.

```mermaid
sequenceDiagram
    participant U as User / browser
    participant H as Authenticated HTTP routes
    participant A as PlanningAgent
    participant P as SubscriptionProvider
    participant D as Postgres / WorkspaceStore
    U->>H: Request a plan
    H->>A: Start for authenticated owner
    A->>D: Read workspace and persist run with base revision
    H-->>U: Accepted run
    A->>P: Infer from bounded Corner context
    P-->>A: Structured result
    A->>D: Save result, not plan changes
    U->>H: Poll and inspect proposal
    H-->>U: Current/proposed changes
    U->>H: Explicit Apply
    H->>A: Apply owned run
    A->>D: Check base revision; atomically commit validated changes, receipt, applied status
    D-->>A: Updated workspace
    A-->>H: Applied result
    H-->>U: Updated workspace and run
```

[proposalMutations](packages/shared/src/agent.ts) translates only permitted planning changes into ordinary validated mutations. The agent can propose recipes, meals, future workouts, routines, and targets; it cannot generate intake logs, measurements, or actual workout results. Started, partially recorded, completed, and skipped workouts are protected. These checks belong in server/shared validation, not only in UI copy or model instructions.

Overlapping Apply requests replay a completed application rather than treating its own committed revision as a stale proposal. Administrative timestamps for proposal mutations use the run's completion time, making their receipt fingerprint deterministic across concurrent requests; activity dates and actual recorded training/food remain user-controlled.

Recipe generation returns a draft; food estimation returns clarification or an editable estimate. Neither saves a recipe or food log automatically. Planning results may also be questions or advice with no mutations.

In the Node runtime, run records persist but background tasks still execute in memory in one process. Startup marks interrupted runs failed rather than resuming them. Agent admission is transactionally serialized so asynchronous SQL does not weaken idempotency or concurrency limits. Shutdown stops new agent work, drains accepted handlers/tasks, and closes the PostgreSQL pool. Keep one Corner Node process; Workers support hosted requests without new inference, not distributed execution of these tasks.

## Credentials and provider availability

Corner sessions and ChatGPT authorization are independent. [subscription.ts](apps/server/src/subscription.ts) owns OAuth state/PKCE/session binding, signed identity checks, encrypted credentials, refresh coordination, model discovery, and disconnect/revocation handling. Short PostgreSQL transactions and generation checks preserve connection/disconnect ordering across awaited I/O. Raw provider credentials never belong in browser state, shared models, or workspace exports. Neon owns account email delivery and managed Auth rate limits; verification uses OTP, and the application verification-policy setting must match the branch.

Credential rotation and catalog/model updates re-read and merge the encrypted registration inside an owner-locked transaction. Identity/generation pins prevent writes across reconnects; token writes additionally pin the refresh token they renewed. OAuth callbacks use one registration/version snapshot and an atomic version check. Provider network I/O stays outside these short transactions.

Local ChatGPT authorization currently requires the supported `http://127.0.0.1` browser origin and local deployment gate. Hosted mode disables this connection and has no alternative inference provider. Do not make hosted AI appear available by changing the deployment label, copying a local grant, hardcoding model access, or silently switching billing paths.

## Verification and release boundaries

[verify.mjs](scripts/verify.mjs) owns conservative local profiles, reusing Turbo and the existing isolated test runner. Incomplete or unknown selection never yields a lighter local profile. PR, staging, and main CI always run full verification. Required checks use ordinary GitHub Actions repository-writer trust, not a workflow-specific GitHub App identity. Live branch protections/default changes require the explicit admin configuration command and exact-tip CI on both persistent branches.

Both persistent branches package the already-built full-stack Worker bundle/assets, checksummed SQL, and a self-contained Node migrator/data validator. [release-artifact.mjs](scripts/release-artifact.mjs) verifies format-3 single-Worker payloads and rejects older formats, unsafe configuration, missing/unlisted files, symlinks, traversal, and digest mismatches. Temporary configs relocate paths outside immutable payloads. Qualification exercises prior/candidate/recovered code and mutations on the migrated schema; representative document fixtures are not universal compatibility proof.

The application is unreleased; native oRPC is the initial deployment baseline, not a migration from published REST artifacts. Old application URLs and unpublished REST artifacts are not supported release/recovery targets. No compatibility bridge or maintenance gate is introduced. Future prior/candidate/recovered Worker versions must all use native RPC and retain read/write, idempotency, schema, immutable-artifact, receipt, and data-recovery safeguards.

[release.mjs](scripts/release.mjs) requires actual successful main CI/artifact identities for production's immutable full-stack payload. Production requires protected human approval and staging-review/hotfix evidence. Plans bind the candidate/baseline/schema, deployment and effective configuration, run, and attempt. Serialized effects journal before SQL and switch one `corner` version. Public checks verify its `X-Corner-Version`, canonical origin, assets, and authentication boundaries; code recovery validates current stored documents and never reverses SQL. Lost provider responses/live drift require operator reconciliation. Separately, [.github/workflows/staging.yml](.github/workflows/staging.yml) invokes [staging-preview.mjs](scripts/staging-preview.mjs) after successful exact current push-to-staging CI, rejects PR/fork/foreign/superseded sources, and supplies protected staging credentials. Its native Preview ledger uses task `corner-preview` and payload kind `corner-staging-preview`, separate from production's `corner-release` ledger. It never consumes production approval or changes production traffic. Automatic updates require trusted source merged onto the default branch, an existing production `corner` Worker, and configured Preview isolation and Access.

No PR code receives production or Neon credentials. Dependency caches use normal GitHub branch/merge-ref isolation. Staging's workflow runs only merged trusted staging source after successful push CI; environment secrets remain separate. Same-account Cloudflare tokens are **not** hostile-writer isolation. Human browser/operational attestations are not automated coverage. See [HOSTING.md](HOSTING.md#build-migrate-and-release) for live cutover, credential assumptions, failure/completion states, and recovery limits.

## Agreed evolution and open decisions

The intended product is a hosted service for performance-focused trainees. Daily tracking usability, AI planning quality, and hosted readiness are priorities. The intended hosted AI path is an approved ChatGPT integration; approval, its actual integration contract, and live verification remain prerequisites. Provider references and current limitations are linked from [README.md](README.md#chatgpt-plan-access-current-scope).

Account isolation, private credentials, truthful activity history, and explicit approval remain binding. Persistence uses Neon Postgres and managed Neon Auth; document-shaped storage and the single-process agent lifecycle remain. Existing SQLite accounts are not claimed by matching email: owners establish managed accounts and explicitly import workspace exports. Hosted capacity targets and launch criteria remain open; Cloudflare production and staging use one full-stack `corner` Worker and its isolated native `staging` Preview.
