### Persistence and migrations

- Workspace persistence is relational: metadata/settings, recipes, planned meals, food entries, groceries, requests, routines, sessions/exercises/sets, check-ins, reviews, and scheduled dates. Typed date/numeric/relationship fields support scoped updates and queries; bounded nested content remains JSONB. Live owner-aware FKs and one-food-log-per-plan uniqueness preserve ownership and history. Managed Auth/local fixture bookkeeping remain outside application schema ownership.
- Normal startup returns settings/revision/AI availability; commands return a bounded revision receipt, not lifetime state. Screens use date windows, cursor libraries/history, bounded details, full-range nutrition/training/grocery aggregates, and arbitrarily old latest-weight/per-exercise sources. Session-lifetime query keys and family revision floors reject stale responses at resolution and ingestion; preview-local editing, drafts, shared notifications, and explicit approval remain.
- Owner locks, original-payload fingerprints, retained retry-before-conflict behavior, record-level workout versions, atomic entity/revision/receipt/proposal commits, encrypted credentials, and provider generation safeguards remain. Ordinary manual `expectedRevision` stays optional. Workout timestamp conflict tokens retain monotonic millisecond precision; historical snapshots/provenance survive source edits or deletion.
- JSON import/export is explicit portability, not storage. Export reads a consistent full server snapshot in bounded batches; import preserves supported older formats, orphan historical IDs, units, optional values, and ordering, rechecking emptiness/revision atomically. A separate 32 MiB transfer cap replaces the old total-workspace byte ceiling for normal operations; no transfer-job subsystem is added.
- Native Drizzle history is appended, never rewritten. Ordinary `--apply` migration with `0001_zippy_silver_sable.sql` exclusively locks legacy `workspace_state` and refuses **any** persisted row inside the same migration transaction before retiring it. Explicit `preservingDocumentCutover` (`--preserving-cutover --operation-id <id>`, plus read-only `--inspect-cutover`) converts populated `0000` workspaces in three resumable phases around unchanged `0001`: preflight-validating all documents before native DDL, transactionally archiving raw rows/UTF-8 bytes/revisions and operation/database/schema/SQL provenance in a dedicated recovery schema (`corner_cutover_recovery`, outside the application catalog) before clearing `workspace_state` and adding a `CHECK (false)` fence, applying unchanged native `0001`, and atomically importing each owner with `importRelational` at its original revision and completion marker before read-only `validatePersistedRecords`. Unmarked destination conflicts or foreign operation IDs fail closed; retained recovery archives, managed Auth, credentials/keys, unrelated records, backups, and historical receipts remain preserved.
- Verified empty schema-only staging baselining checks the complete current immutable inventory/catalog, source native history, target/Auth emptiness, and database identities before recording verified migration identities. Local pre-Drizzle adoption refuses retained document rows before baseline commitment; startup itself never applies schema changes.
- Release qualification explicitly identifies storage generation. The first document-to-`relational-v1` boundary is `forward-only` for empty databases or `preserving` when explicitly qualified with `--preserving`, never bootstrap or a supported old-code rollback. Later compatible relational qualification retains prior/candidate/recovered reads, writes, retries, and bounded current-record validation in one consistent read-only snapshot. Format-4 artifact/security/native-history/receipt safeguards remain; old evidence is never relabelled and SQL is never rewound. The live cutover procedure is in [HOSTING.md](HOSTING.md#relational-storage-cutover).
- Release qualification captures full previous-workspace snapshots through `workspace/export` for relational artifacts and `workspace/get` for document artifacts; relational bootstrap metadata is never compared against a full export. Preservation checks compare the real `logs` collection after follow-up writes.
- Migration connection-loss regressions assert rejection, persisted recovery phases, and exact resumed records without depending on timing-sensitive PostgreSQL driver error wording.

### Delegation and data safety

- Delegated connections are optional and separate from Corner login. An approved external client may use its selected permissions autonomously until its grant expires or is revoked; granted nutrition writes/deletes need no per-change Corner approval. Choose clients and permissions accordingly. Corner neither gains that client's conversations/memories nor hosts its model execution.
- These connections expose implemented reads, dated meal-plan create/edit and food-log/recipe CRUD only. Deletes require separate owner-selected permissions. Recipe-in-use rejection, one-log-per-plan uniqueness and historical food snapshots remain intact; recipe changes/deletion do not rewrite or cascade logs. Retired model connections, proposal/apply executors, food-recording assistance and training assistance are not restored; historical provider grants must not be repurposed as MCP credentials.
- Preserve installation keys, private configuration, original SQLite backups, and independent production/staging backups. Database restore is a separate operator-controlled data-loss decision. Source cleanup does not authorize cloud/admin/data changes or retirement of provider resources.
