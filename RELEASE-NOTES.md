# Changelog

## Unreleased

Corner has not been released. This is the current implementation baseline, not a record of a public launch, live configuration, or completed deployment. Setup commands live in [README.md](README.md); operator procedures and recovery gates live in [HOSTING.md](HOSTING.md).

### Application and workspace

- pnpm/Turborepo workspaces separate the Hono server, Vite/React product, backend-free design catalog, shared UI, domain rules, and browser-safe API contract.
- Application calls use native oRPC at `/api/rpc` and TanStack Query browser server state. Managed Auth `/api/auth`, OAuth `/auth/callback`, and `GET /api/health` remain separate protocols.
- Managed Neon Auth owns accounts, sessions, verification, and recovery delivery. Owner-scoped PostgreSQL workspaces retain recipes, meals, groceries, food logs, workouts, routines, targets, and progress records. Profile editing is optional; sign-in opens the requested workspace route without onboarding.
- Sign-in confirms the server-side Corner session before replacing the account form or retiring private query state. A successful Auth response followed by a missing session now shows an actionable error and preserves the email for retry. Unverified accounts receive policy-appropriate verification guidance rather than an empty sign-in form.
- Account credentials, verification/recovery inputs, and the workspace import confirmation use TanStack Form with the existing shared controls and native constraints. Account mode changes still retain email while clearing passwords and codes; request cancellation and Corner session confirmation remain separate safety boundaries. Import confirmation resets with each selected file, and commits retain the matching preview’s candidate, request ID, and revision.
- Read-only workspace queries recover transient `ACCOUNT_SERVICE_UNAVAILABLE` failures with two cancellable backoff retries, preserving the session, revision ordering, and manual Retry after exhaustion. Mutations and genuine sign-in failures do not retry.
- Managed-session failures emit sanitized category/status/duration/procedure/version diagnostics correlated by a generated `X-Corner-Request-Id`; Worker API responses include their serving `X-Corner-Version`. No session cache or validation bypass is added.
- Account-entry headings preserve the space between “for” and “your” on phones and in accessible text while retaining the desktop line break.
- Shared Base UI-backed controls, navigation, light tokens, and toast notifications serve the product and catalog. The catalog also supports dark appearance. Product routes are bookmarkable; local drafts and filters survive navigation.
- Workout/routine editors, check-ins, and skip confirmations use TanStack Form for editable values, validation, and pending submissions. Workout suggestions remain unrecorded until explicitly confirmed; ID-keyed prefill intent preserves cleared optional inputs through reordering/removal, including imported dotted IDs and set IDs reused by different exercises. Save and Complete remain distinct intents, native constraints still apply, and dialogs close only after successful saves.
- Catalog submission examples now use pinned TanStack Form 1.33.5 for editable values, including local searches, dialog drafts, controlled country selection, and Questionnaire answers. Shared controls, native constraints, local synthetic results, and no-network behavior are retained; this is not a claim that all product forms are migrated.
- Corner supports iPhone Home Screen installation with a standalone manifest, opaque app icons, and Apple metadata, retaining the existing mobile navigation and safe-area layout. Production-only, network-only service-worker handling shows a reconnect page for disconnected launches without caching private data or queueing edits. Installation and real-iPhone verification steps are in [README.md](README.md#install-on-iphone).
- Original Corner JSON imports remain previewed, revision-checked, and restricted to empty workspaces. Workspace export and recipe text downloads remain supported. Imports do not claim identities by email or transfer passwords, sessions, model grants, or separate agent history.
- Removed unused sample recipe/starter-week/template APIs and date selectors; persistence reuses the shared empty training-state factory. Supported original Corner imports and manual workflows remain unchanged.
- Domain code is separated into nutrition, training, workspace, and agent packages with direct owner imports and acyclic dependencies. Development watchers, Vite access boundaries, containers, source packaging, and release tooling use those packages; no catch-all package or compatibility re-exports remain.
- Server, domain, and oRPC contract validation now use Zod 4. Planning tools use native JSON Schema conversion instead of a direct `zod-to-json-schema` dependency; migration inventory validation retains UUID-shaped snapshot lineage IDs and explicit string-keyed table records.
- Manual profile/targets, recipes, food logging, and meal selection now use TanStack Form `1.33.5` for editable drafts and submission state while retaining shared controls and native constraints. Saves await persistence, failed saves retain edits, food estimates only populate review, matching ingredient metadata survives recipe edits, and unset targets remain distinct from zero targets. Recipe editing also retains legitimate zero-minute prep/cook values.

### Local development

- `pnpm dev` owns local PostgreSQL 17, an HTTPS Better Auth fixture, and the API/web/catalog/compiler tasks. It does not connect to cloud Neon or load root environment files.
- `dev:seed` explicitly creates independent empty/demo synthetic accounts. Persistent seed identities and completion records preserve fixture edits and recover interrupted seeding. No staging or production seed target exists.
- Repeated startup reuses only the authenticated controller for this checkout. `dev:down` preserves records and keys; confirmed `dev:reset` deletes only the owned local database and retains keys. Unrelated listeners, existing environment files, and repository `data/` are not modified.
- The local fixture sends no email or model requests and is not qualification of live Neon Auth, OTP, or password-recovery delivery.
- Web tests use Vitest 5 with sequential isolated forks, React Testing Library/jsdom for production components, and Node environments for configuration/service-worker checks. React Test Renderer, warning suppression, and generated React test bundles are removed.
- Full verification adds Playwright journeys in Chromium desktop and emulated iPhone WebKit for account separation, food logging, and recorded workout persistence. The browser harness reuses disposable PostgreSQL/HTTPS Auth fixtures with temporary keys and owned-process cleanup; intercepted provider redirects block service workers to avoid bypassing synthetic responses. This does not qualify live OAuth, email delivery, or real-iPhone installation.

### Persistence and migrations

- Workspace persistence is relational: metadata/settings, recipes, planned meals, food entries, groceries, requests, routines, sessions/exercises/sets, check-ins, reviews, and scheduled dates. Typed date/numeric/relationship fields support scoped updates and queries; bounded nested content remains JSONB. Live owner-aware FKs and one-food-log-per-plan uniqueness preserve ownership and history. Managed Auth/local fixture bookkeeping remain outside application schema ownership.
- Normal startup returns settings/revision/AI availability; commands return a bounded revision receipt, not lifetime state. Screens use date windows, cursor libraries/history, bounded details, full-range nutrition/training/grocery aggregates, and arbitrarily old latest-weight/per-exercise sources. Session-lifetime query keys and family revision floors reject stale responses at resolution and ingestion; preview-local editing, drafts, shared notifications, and explicit approval remain.
- Owner locks, original-payload fingerprints, retained retry-before-conflict behavior, record-level workout versions, atomic entity/revision/receipt/proposal commits, encrypted credentials, and provider generation safeguards remain. Ordinary manual `expectedRevision` stays optional. Workout timestamp conflict tokens retain monotonic millisecond precision; historical snapshots/provenance survive source edits or deletion.
- JSON import/export is explicit portability, not storage. Export reads a consistent full server snapshot in bounded batches; import preserves supported older formats, orphan historical IDs, units, optional values, and ordering, rechecking emptiness/revision atomically. A separate 32 MiB transfer cap replaces the old total-workspace byte ceiling for normal operations; no transfer-job subsystem is added.
- Native Drizzle history is appended, never rewritten. Ordinary `--apply` migration with `0001_zippy_silver_sable.sql` exclusively locks legacy `workspace_state` and refuses **any** persisted row inside the same migration transaction before retiring it. Explicit `preservingDocumentCutover` (`--preserving-cutover --operation-id <id>`, plus read-only `--inspect-cutover`) converts populated `0000` workspaces in three resumable phases around unchanged `0001`: preflight-validating all documents before native DDL, transactionally archiving raw rows/UTF-8 bytes/revisions and operation/database/schema/SQL provenance in a dedicated recovery schema (`corner_cutover_recovery`, outside the application catalog) before clearing `workspace_state` and adding a `CHECK (false)` fence, applying unchanged native `0001`, and atomically importing each owner with `importRelational` at its original revision and completion marker before read-only `validatePersistedRecords`. Unmarked destination conflicts or foreign operation IDs fail closed; retained recovery archives, managed Auth, credentials/keys, unrelated records, backups, and historical receipts remain preserved.
- Verified empty schema-only staging baselining checks the complete current immutable inventory/catalog, source native history, target/Auth emptiness, and database identities before recording verified migration identities. Local pre-Drizzle adoption refuses retained document rows before baseline commitment; startup itself never applies schema changes.
- Release qualification explicitly identifies storage generation. The first document-to-`relational-v1` boundary is `forward-only` for empty databases or `preserving` when explicitly qualified with `--preserving`, never bootstrap or a supported old-code rollback. Later compatible relational qualification retains prior/candidate/recovered reads, writes, retries, and bounded current-record validation in one consistent read-only snapshot. Format-4 artifact/security/native-history/receipt safeguards remain; old evidence is never relabelled and SQL is never rewound. The live cutover procedure is in [HOSTING.md](HOSTING.md#relational-storage-cutover).
- Release qualification captures full previous-workspace snapshots through `workspace/export` for relational artifacts and `workspace/get` for document artifacts; relational bootstrap metadata is never compared against a full export. Preservation checks compare the real `logs` collection after follow-up writes.
- Migration connection-loss regressions assert rejection, persisted recovery phases, and exact resumed records without depending on timing-sensitive PostgreSQL driver error wording.

### Hosting and release controls

- Cloudflare production uses one full-stack Worker, `corner`. Staging uses isolated native Preview `staging` under that Worker, not separate frontend/backend or staging Workers. Both consume identical immutable format-4 bundle/assets/Drizzle migrator bytes without rebuilding.
- Expected origins are `https://corner.adam-nathaniel-woo.workers.dev` and `https://staging-corner.adam-nathaniel-woo.workers.dev`; production may instead use an exact HTTPS custom domain. Preview URLs stay enabled; Access protects only staging's stable/deployment URLs, never production.
- Persistent staging retains its schema-only Neon branch, independent Auth/keys, and synthetic records. Feature branches use local checks; per-PR database/app provisioning and independent Cloudflare build deployments are not supported.
- Access-gated synthetic staging requires email verification disabled in both its application configuration and independent Auth policy, allowing made-up test emails. Production continues requiring verification. Existing staging settings must be aligned through separately authorized operator work without resetting records, accounts, or keys; see [HOSTING.md](HOSTING.md#configure-the-origin-and-secrets).
- After explicit operator cutover, features target persistent `staging`; releases promote staging to `main` with merge commits and synchronize main back afterward. Exact-tip full CI, branch/environment protection read-back, and live setup remain separate gates, not effects of a source change.
- Linux CI bypasses the Azure Ubuntu archive mirror before installing Playwright system dependencies, retaining standard Ubuntu mirrors, both browser engines, and the full verification gate.
- Format-4 artifacts bind complete migration metadata and file inventories. Verification rejects unsafe or altered payloads without executing packaged code. Production retains one-version receipts, schema-attempt journals, and public probes. Staging uses its own Preview ledger, not production receipts.
- Main promotion now requires GitHub's native successful-deployment rule for the `staging` environment, alongside full CI, with no bypass actors. The policy helper maintains and reads back this main-only ruleset while preserving unrelated rules; emergency fixes also require staging.
- Staging explicitly reports a `Staging deployment` commit status for the exact workflow SHA so the promotion PR shows pending/success/failure even when dispatched jobs are omitted from its check rollup. Green requires successful verification of that same SHA; setup failures, cancellation, and missing/mismatched verification cannot report success. Skipped listeners publish no status, and wrong-branch dispatches fail the staging environment's branch policy.
- Staging public verification waits for the exact serving version before testing security boundaries and reports safe, specific failures. Migration/public failures finish their journal statuses. A pinned completion operation verifies an already-deployed Preview without uploading again or touching SQL, preserving failed-run history and production traffic.
- Merging to main is ordinary production release approval. Successful current push-to-main CI triggers a credential-free workflow that dispatches `release.yml` on main, keeping production credentials main-only even when staging is the repository default. The controller qualifies the exact immutable artifact, rechecks current main before planning/SQL/traffic changes, preserves migration and live-baseline safeguards, and completes after public probes. Repeated CI for an already-deployed source probes it without redeploying. Automatic releases do not claim human browser verification.
- Removed production environment reviewer gates, manual-review JSON, per-path human completion classification, and the separate operational-validation workflow. Explicit bootstrap/adoption, preserving cutover/resume, recovery, and configuration releases now use the same main-only `production` environment and existing credentials as ordinary releases, completing after automated checks. Staging is the review surface before promotion to main. The CI policy helper configures only staging and production and needs no reviewer identity. Exact CI/artifact, execution, schema, live-version, and explicit bootstrap/adoption/cutover/recovery safeguards remain; no human browser or inbox evidence is implied.
- Production deployment statuses now finish with their actual stage outcomes: qualification succeeds the plan, migration succeeds or fails its retained schema-attempt journal, and failed live/public checks fail the incomplete deployed receipt. Explicit operator preserving cutovers (`preserving_cutover: true`, `operation_id`) package and upload an isolated `worker/maintenance-worker.js` gate (503/`Retry-After`/`no-store` without PostgreSQL or Neon Auth forwarding), journal `maintenance-uploaded`, `maintenance-active`, `cutover-validated`, `maintenance-complete`, and (only when database cutover is still `untouched`) `maintenance-aborted` in `production-maintenance`, inspect durable database cutover state before resuming or aborting, and return live traffic to the pinned `maintenanceVersionId` if public probes fail after switching to the relational candidate. Successful promotion and completion retry retire the consumed plan and intermediate production receipts while preserving the completed baseline. Older successful plan/schema/maintenance journals become inactive without deleting payloads or migration history.
- Recovery restores compatible code only, never SQL or old data, and retains qualified artifact bytes, attempted-schema validation, immutable history, receipt lineage, and verified live identity. Document-only code is not a recovery target after `relational-v1`; the first relational boundary requires reviewed forward repair. Lost provider responses or unrecorded deployments require reconciliation, not blind retry.
- The optional single-server Docker/Caddy deployment remains supported. Keep one Node process for in-memory agent tasks. Workers use request-scoped database pools and do not start inference or process-wide agent recovery.

### AI and data safety

- Local ChatGPT authorization remains optional and independent of Corner login. Tokens stay encrypted server-side; disconnect, refresh rotation, and session/generation checks remain protected.
- AI produces reviewable proposals, recipe drafts, and editable food estimates. Explicit approval is required to apply planning changes; stale proposals and edits to protected recorded workouts are rejected. AI cannot record food eaten, measurements, or completed training on the user's behalf.
- Hosted ChatGPT access remains disabled pending an approved integration and live qualification. Local grants must not be repurposed for public hosting; no separately billed fallback is enabled.
- Preserve installation keys, private configuration, original SQLite backups, and independent production/staging backups. Database restore is a separate operator-controlled data-loss decision. Source cleanup does not authorize cloud/admin/data changes or retirement of provider resources.
